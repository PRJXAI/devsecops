# Verify tool images

1. Read AGENTS.md and the inventory/results. Never use real credentials, vaults, cloud accounts, current kubecontext or unapproved remote Docker engines.
2. Run cargo fmt --all -- --check, cargo clippy --all-targets --locked -- -D warnings and cargo test --locked. Run `cargo run --locked --bin devsecops -- check-all` for serial native build/version checks, then `contract TOOL` for each tool's filesystem/functional prerequisites. Unsupported contracts fail, not skip. `audit-dependencies` is the private captured first-party lockfile gate. `catalog-tool TOOL` requires GITHUB_SHA and captures public native inventories/identities for review, never clean receipts; inspect `catalog-evidence-TOOL-{amd64,arm64}`. `prepare-tool TOOL` requires GITHUB_SHA and adds mandatory contracts/inventory coverage/scans/artifacts; `publish-tool TOOL` is restricted to the approved main-branch manual workflow and that tool's readiness record. Workflow launchers pass the allowlisted identity through DEVSECOPS_TOOL, not shell interpolation. Both architectures remain mandatory, but sibling releases and experimental candidates must not be prerequisites. Keep command/container lifetimes and resources bounded.
3. For the owner-authorized upgraded Gitleaks candidate, explicitly run `cargo test --locked --bin devsecops release::gitleaks_candidate::native_gitleaks_dependency_candidate -- --ignored --exact`. It shares production's fixed-source/patch compiler step, but keeps a separately labeled fixture and records only `.work/gitleaks-native-candidate/` functional/inventory evidence, not production handoffs. Both recipes now package the checked Go notices; production separately requires its upgraded captured profile. Refuse stale output; retain failed observations before a corrected rerun. Both native CI runners execute it independently of failed production preparation. Its outputs are not scans, release receipts or approval; follow docs/release-blockers.md.
4. Verify each final image's UID/entrypoint, version, architecture, CA roots and absence of forbidden executables. Gitleaks also requires the exact collected Go notice bytes at mode 0444. Save/export stdout must retain pre-write archive bounds, create-only files, EOF/deadline/cancellation checks and bounded cleanup; ordinary streams remain capped at 8 MiB. The stopped-container filesystem test uses the same endpoint-bound build-only path, without smoke execution. `check`/contracts separately execute the loader/library closure. Neither ELF headers nor a version string establishes complete native acceptance.
5. Exercise meaningful contracts: Syft formats/input coverage, Grype offline detection with separately fresh DB, Gitleaks seeded source/deleted bare history/redaction, kustomize rendering, kubectl offline client, Docker Compose config, Cargo audit/deny with curated metadata/DB/source inputs. Clearly mark any contract not executed.
6. Keep scanners network-disabled and socket-free; isolate read-only inputs from output/cache. Docker/k3d control-plane access is privileged and separate. Do not create a real cluster or contact one for a version test.
7. Preserve all findings and raw private diagnostics. Follow docs/release-risk-policy.md: exact owner-reviewed no-fix/no-alternative cases may pass as accepted-risk; the exact pinned Grype precision notice is informational only for its known offline scan. All other findings/diagnostics/errors block. Check embedded binary/native dependencies as well as OS packages. Validate captured named/location/compiler tuples from unchanged real native output at producer and publisher; missing/UNKNOWN inventories and unreviewed architectures block. Never populate scanner reports from expectations. Do not call an image clean merely because it has no package manager or fewer packages.
8. Keep raw output private in ignored .work; publish only approved statuses/counts/identities. Record exact results and license/source/provenance gaps. Only the approved main-branch manual workflow may publish after native checks, complete all-severity/ignored-match accounting, zero unapproved findings and redistribution review pass. Schema-3 receipts and published release-status.json must retain accepted-risk status, exact exception IDs and counts. Never claim consumer compatibility from version smoke or bypass a failed gate.
