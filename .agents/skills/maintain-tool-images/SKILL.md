# Maintain tool images

1. Read AGENTS.md, README.md, docs/tool-inventory.md and docs/results.md. Inspect the actual consumer workflow/callers; never infer required behavior from a tool name alone.
2. Prefer a released, checksum/digest-pinned binary over a maintained fork. Verify linux/amd64 and linux/arm64 artifacts, version, executable path, loader/dependency closure and license/source obligations. Official GNU cargo-audit copies only the individually verified architecture-specific runtime files; do not replace that with a whole dynamic base or assume top-level notices complete transitive obligations.
3. Update the smallest explicit Dockerfile. Gitleaks is the one reviewed fixed-source derivative: preserve its pinned source/patch/compiler, offline race tests, exact private context, notice bytes and upgraded production inventory; never accept a caller-supplied executable or restore the old supplier-profile fallback. Final image must be pinned distroless/nonroot with no shell/package manager/compiler/config/secrets/DB. Do not add a template engine, generic rebuild framework or arbitrary scanner override.
4. Keep retrieval separate from offline use. Preserve CA roots, HOME/cache paths, writable tmpfs needs, exit codes, output formats, history coverage/redaction and resource bounds. Git-dependent tools must include and test a working Git closure.
5. Run Rust policy/unit tests, endpoint-bound native builds and `contract TOOL`; use the actual code paths in AGENTS. A cross-build/version string is insufficient. Review native unchanged catalog evidence before updating captured tuple/compiler expectations; do not infer UNKNOWN versions, use package counts or rewrite reports. Record architecture, identities, exact failures and blocked checks.
6. Update inventory/results and maintenance docs. Dependabot PRs never auto-merge; coordinate literal artifact hashes, runtime closure and Rust expected-version contracts. Obtain owner review before changing consumer pins; publication is only through the explicitly approved main-branch manual workflow. Fresh SBOM/vulnerability/license/source/provenance checks and explicit registry authorization remain prerequisites. Exact owner-selected current-stack cases (including fixable findings) and the separately bounded Gitleaks no-fix rule follow docs/security.md; retain findings and accepted-risk status, never a clean claim or blanket severity exemption. That tool's `.github/publication-readiness/TOOL.json` must explicitly approve all fields and have no blockers; manual inputs cannot override it or borrow another tool's approval. Preserve separate release identities, both-architecture validation and tool/source-bound approval. Preserve the documented runner/producer trust and missing host-disk-quota limitations.
